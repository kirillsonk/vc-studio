# Выкладка Сборки на Timeweb

Подготовлено 6 октября 2026. Код находится в ветке `dev`. В `main` переносим только после фразы владельца «пушим в main». Force push не используем

Создание платных ресурсов, изменение DNS и переменных окружения выполняем после отдельного явного «да». Ключи вводятся в защищенные поля панели или берутся из согласованного защищенного локального файла для первичного создания окружения. Содержимое файла не выводим в переписку, логи или команды, не копируем в Git, Dockerfile и build arguments

## Схема

Посетитель → Next.js в Москве → общий ретранслятор → OpenAI или Telegram

Next.js также обращается к отдельной постоянной PostgreSQL. Она хранит счетчики ограничений, состояние доставки и номера заявок. Содержимое контейнера не используем для хранения данных. Повторный деплой приложения не должен сбрасывать базу

Существующий контракт формы сохранен:

- `GET /api/intake/config`: доступность отправки
- `POST /api/intake/next`: следующий вопрос или бриф
- `POST /api/intake/submit`: подтвержденная заявка
- `GET /api/analytics/config`: публичный ID Метрики
- `/api/brief` и `/api/lead`: дополнительные адреса для тех же запросов next и submit

Серверная логика общая с Sites Worker. PostgreSQL-адаптер заменяет только доступ к базе, вопросы, валидация и доставка остаются в существующих модулях

## Окружение приложения

Переменные задаются при запуске контейнера. Для сборки секреты не нужны. При первичной настройке можно прочитать значения из указанного владельцем локального файла с правами только для владельца и передать непосредственно в защищенный интерфейс окружения. Файл не прикладываем к задаче и не сохраняем в репозитории

| Переменная | Назначение |
| --- | --- |
| `PUBLIC_ORIGIN` | `https://sborkadigital.ru`, обязательный адрес для проверки Origin |
| `DATABASE_URL` | Приватная строка подключения к постоянной PostgreSQL |
| `RELAY_URL` | HTTPS-адрес общего ретранслятора без пути и параметров |
| `RELAY_SECRET` | Отдельный пароль клиента Сборки, минимум 32 символа |
| `RELAY_CLIENT` | `sborka` |
| `OPENAI_MODEL` | `gpt-6-luna`, выбрана владельцем 6 октября |
| `YANDEX_METRIKA_ID` | `113480948` |
| `TRUST_PROXY` | Сначала оставить пустым, см. ниже |

На сервере Сборки при работе через ретранслятор не нужны OpenAI API key и Telegram bot token. Для локального прямого режима поддерживаются `OPENAI_API_KEY` или прежний `CHATGPT_PLATFORM_API_KEY`, а также `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`

`NEXT_PUBLIC_*` встраиваются при сборке и публичны. Секреты в них не помещаем. Форма по умолчанию использует `/api/intake`

Для подключения PostgreSQL выбираем защищенный канал и настройку проверки сертификата согласно параметрам выданного подключения. Не отключаем проверку TLS для подключения через публичную сеть

## Таймауты и контекст

На один запрос AI отводится 19 секунд целиком, включая чтение ответа. Допускается один повтор при быстром сетевом сбое, HTTP 429 или 5xx. Истекший таймаут не повторяем. Клиент ждет ответ 22 секунды и затем продолжает локальный сценарий без потери ответов

В новый запрос передаются исходная задача и вся история ответов. Если сериализованный запрос к ретранслятору превышает 64 КиБ, его не обрезаем и не отправляем заведомо неуспешный запрос. Используется локальный бриф со всеми ответами, правки человека сохраняются

Общий ретранслятор ограничивает каждый клиент отдельно: до 60 запросов AI и до 60 сообщений Telegram в минуту. На доставку одной заявки, включая все части, сервер отводит 40 секунд, на отдельный внешний вызов до 30 секунд. Клиент ждет отправку до 45 секунд. Подтвержденные части сохраняются в базе; после неоднозначной ошибки не отправляем их заново вслепую

## IP и Origin

Входящий `CF-Connecting-IP` удаляется: на Timeweb его может прислать сам посетитель. Без `TRUST_PROXY` приложение использует общий лимит, никаким IP из произвольных заголовков не доверяет. Для AI действует общий лимит 90 запросов в минуту, при подтвержденном IP лимит 24 запроса в минуту. Общий дневной предел 1000 запросов

После проверки, что приложение доступно только через доверенный ingress и тот перезаписывает заголовки, можно выбрать:

- `TRUST_PROXY=x-real-ip`: доверять одному проверенному адресу в X-Real-IP
- `TRUST_PROXY=xff:1`: брать первый адрес справа в X-Forwarded-For
- `TRUST_PROXY=xff:N`: брать адрес с учетом известного числа доверенных прокси справа

Не включать этот режим только потому, что заголовок присутствует. Сначала подтвердить схему ingress. Значение `true` не поддерживается

Origin запроса сравнивается с `PUBLIC_ORIGIN`, а не с присланными Host и X-Forwarded-Host. `www.sborkadigital.ru` перенаправляется на `sborkadigital.ru` постоянным redirect в standalone-режиме

## Сборка и база

Обычная сборка для Sites сохранена:

```sh
npm ci
npm run check:copy
npm run typecheck
npm run test:intake
npm run test:node
npm run build
```

Сборка для Node:

```sh
npm run build:node
```

`NEXT_STANDALONE=1` включает output standalone и серверный файл `route.node.ts`. Обычная статическая сборка этот API-файл не считает маршрутом

Корневой Dockerfile собирает Node 22 standalone в несколько этапов. Готовый контейнер запускается от пользователя `node`, слушает порт 3000, команда запуска `node server.js`

Первый раз создать схему отдельной командой с настроенным `DATABASE_URL`:

```sh
npm run db:migrate:postgres
```

В готовом контейнере та же команда:

```sh
node scripts/migrate-postgres.mjs
```

Миграции из `postgres/migrations` применяются в транзакции с блокировкой и проверкой контрольной суммы. Сервер не создает таблицы при пользовательских запросах. При отсутствии подключения отправка не становится успешной и не переходит на временную базу

При переносе существующих данных D1 отдельно сохранить номера из `intake_receipts` и состояния доставки, которые еще нужны для безопасных повторов. После импорта номеров установить последовательность PostgreSQL на их максимум. Это отдельный шаг переноса, миграция схемы сама данные не импортирует

## Порядок запуска

1. Проверить сборку и локальную работу на 390 и 1440 px
2. Владелец добавляет `vc-studio` и `ai-relay` в доступ GitHub App Timeweb через https://github.com/settings/installations, сохраняя доступ Flame. На 6 октября интеграция видит только `flame-dev-landing`
3. После отдельного разрешения «пушим в main» перенести проверенный код в main обоих репозиториев
4. Согласовать платные ресурсы и первичное окружение. Создать постоянную PostgreSQL в Москве и общий ретранслятор в Нидерландах
5. Владелец сохраняет выданную Timeweb строку подключения к БД из панели в защищенный локальный файл. Пароль генерирует Timeweb, MCP не возвращает его
6. Создать приложение сайта в Москве из main с корневым Dockerfile и окружением, включить автодеплой сайта. Применить миграции, при необходимости перенести существующие номера и состояния доставки
7. Убедиться, что нужный коммит уже запущен, проверить config, бриф, сохранность данных после перезапуска и идемпотентность доставки. Для тестовой доставки использовать согласованный чат Сборки `-5473838680`, текст явно начинать с `ТЕСТ`
8. Отдельно после разрешения добавить основной домен и www, изменить DNS на адрес приложения, дождаться SSL
9. Проверить сообщение в чате Сборки и отсутствие отправки в чат Flame dev

По каталогу Timeweb на 6 октября: приложение в Москве, preset 2731, 510 рублей в месяц; ретранслятор в Нидерландах, preset 1631, 510 рублей; PostgreSQL в Москве, preset 1139, 496 рублей. Каждое приложение требует отдельного публичного IP. Для базы предварительно также заложен публичный IP с проверяемым TLS. По https://timeweb.cloud/prices IPv4 стоит 200 рублей в месяц. Предварительный итог 2116 рублей в месяц, без резервных копий и расходов OpenAI. Точную конфигурацию сети и цену проверяем перед заказом

Окружение можно передать через MCP при создании приложения. Последующее изменение переменных и удаление ресурсов доступны только в панели. Каждый платный запрос MCP сначала возвращает конкретную операцию для подтверждения владельцем, а выполняется только после его ответа

Владелец разрешил использовать существующий чат Сборки для теста с префиксом `ТЕСТ`. Новый чат для этого не требуется. Отсутствие ошибки HTTP само по себе не подтверждает доставку: проверяется само сообщение в согласованном чате

## Откат

Сохранить предыдущий рабочий образ или коммит перед обновлением. При проблеме вернуть его через панель, оставив ту же PostgreSQL и серверные настройки. Не удалять таблицы и не сбрасывать номера заявок. Перед изменением схемы сделать резервную копию. Разрушающие миграции требуют отдельного плана отката

Не удалять старый ретранслятор Flame dev: его переключение выполняется последним отдельным шагом после проверки общего сервиса

## Что проверено локально

Тесты адаптера проверяют отдельную передачу параметров SQL, атомарный запрос лимита, изоляцию Origin, обработку доверенных прокси, адреса API и отсутствие временной базы при сбое настройки

Реальный PostgreSQL integration и запуск Docker image пока не проверены: PostgreSQL локально не установлен, Docker daemon выключен. До продового переключения проверить миграции, параллельную отправку одной заявки и сохранность номеров после перезапуска на постоянной базе
